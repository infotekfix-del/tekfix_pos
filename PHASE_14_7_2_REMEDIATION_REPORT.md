### TASK 1: ROOT CAUSE ANALYSIS

#### 1.1 The Anomaly
The audit app crashed when attempting to verify the signature generated by the Android Keystore with:
`FormatException: Invalid radix-16 number (at character 1) ME ^`.

#### 1.2 Binary & Cryptographic Data Flow Trace
1. **Hardware Signing Mechanism (`MainActivity.kt` lines 200–205):**
   ```kotlin
   val s = Signature.getInstance("SHA256withECDSA")
   s.initSign(privateKey)
   s.update(payloadBytes)
   val signatureBytes = s.sign()
   val sigBase64 = Base64.encodeToString(signatureBytes, Base64.NO_WRAP)
   result.success(sigBase64)
   ```
   Java's `Signature.getInstance("SHA256withECDSA").sign()` produces an **ASN.1 DER** sequence:
   $$\text{SEQUENCE} \; (0x30) \; \Vert \; \text{length} \; (0x44 \text{ to } 0x45) \; \Vert \; \text{INTEGER } r \; \Vert \; \text{INTEGER } s$$

2. **Base64 Encoding Transformation:**
   The first two bytes of ANY valid ASN.1 DER ECDSA signature are:
   - Byte 0: `0x30` (`0011 0000` in binary)
   - Byte 1: `0x44` or `0x45` (`0100 0100` or `0100 0101` in binary)
   
   Splitting these 16 bits into 6-bit Base64 chunks:
   - Chunk 1: `001100` $\rightarrow$ Decimal 12 $\rightarrow$ Character **`'M'`**
   - Chunk 2: `000100` $\rightarrow$ Decimal 4 $\rightarrow$ Character **`'E'`**
   
   Therefore, **every standard ASN.1 DER ECDSA signature encoded in Base64 fundamentally begins with `"ME..."`**.

3. **The Parser Failure in `hardware_audit_screen.dart` (pre-fix line 189):**
   ```dart
   final sigBytes = <int>[];
   for (var i = 0; i < sigHex.length; i += 2) {
     sigBytes.add(int.parse(sigHex.substring(i, i + 2), radix: 16));
   }
   ```
   The Dart code named the incoming variable `sigHex`, erroneously presuming that `signPayload` had returned a hexadecimal string. When it attempted:
   ```dart
   int.parse("ME", radix: 16)
   ```
   Radix-16 strictly requires characters `[0-9a-fA-F]`. The character `'M'` triggered a fatal `FormatException`, aborting the audit suite before tests 6–10 could complete.

### TASK 2: CRYPTOGRAPHIC REMEDIATION

#### 2.1 Dart Side: Byte-Safe Signature Parser (`lib/audit/hardware_audit_screen.dart`)
We introduced `_parseSignatureBytes()` which handles both Base64 and Hex encodings safely without guessing or crashing:

```dart
Uint8List _parseSignatureBytes(String rawSig) {
  final trimmed = rawSig.trim();
  final hexRegex = RegExp(r'^[0-9a-fA-F]+$');
  if (trimmed.length % 2 == 0 && hexRegex.hasMatch(trimmed) && trimmed.startsWith('30')) {
    final bytes = <int>[];
    for (var i = 0; i < trimmed.length; i += 2) {
      bytes.add(int.parse(trimmed.substring(i, i + 2), radix: 16));
    }
    return Uint8List.fromList(bytes);
  }

  // Standard Android Keystore ASN.1 DER Base64 format (starts with "ME...")
  try {
    return Uint8List.fromList(base64Decode(trimmed));
  } catch (_) {
    try {
      final bytes = <int>[];
      for (var i = 0; i < trimmed.length; i += 2) {
        bytes.add(int.parse(trimmed.substring(i, i + 2), radix: 16));
      }
      return Uint8List.fromList(bytes);
    } catch (_) {
      return Uint8List(0);
    }
  }
}
```

### TASK 3: HARDWARE ENCLAVE CLASSIFICATION RULES

On the TECNO KM9 (and many modern MediaTek/Qualcomm devices):
- **StrongBox Keymaster:** Not present (`hasStrongBoxFeature == false`). StrongBox requires a dedicated second secure element chip (e.g. Titan M2), which is only present on select high-end Pixel and Samsung Enterprise devices.
- **Trusted Execution Environment (TEE):** Fully present and active (`isInsideSecureHardware == true`, `securityLevel: "hardware_tee"` / `"TEE_BACKED"`). The private key is generated and stored inside ARM TrustZone hardware.

**Classification Logic:**
- If `keySecurityLevel == 'STRONGBOX_BACKED'`: Verdict is **`STRONGBOX_BACKED`**.
- If `keySecurityLevel == 'TEE_BACKED'` OR `keySecurityLevel == 'hardware_tee'` OR `isInsideSecureHardware == true`: Verdict is **`VERIFIED: TEE (TRUSTZONE) HARDWARE BACKED`**.
- Only if `isInsideSecureHardware == false` and software emulation is detected does it downgrade to `SOFTWARE_BACKED`.

This preserves full hardware security integrity without falsely disqualifying genuine ARM TrustZone TEE devices.
